# Deploying private-rag on Enclave OS Virtual

This recipe boots a per-fleet `private-rag` enclave with a colocated `pgvector/pgvector:pg17` Postgres instance, both reached over RA-TLS via the manager's `/api/v1/containers` API. Both containers receive their config exclusively through `LoadRequest.Env`; nothing is baked into the images, so the same `@sha256` digests can be reused across fleets.

## Two containers per fleet

### 1. Postgres + pgvector (internal)

```jsonc
{
  "name":     "rag-db",
  "image":    "docker.io/pgvector/pgvector@sha256:<pin>",
  "port":     5432,
  "internal": true,
  "storage":  "10G",
  "env": {
    "POSTGRES_PASSWORD": "<random per-fleet, generated by the orchestrator>",
    "POSTGRES_DB":       "rag",
    "PGDATA":            "/data/pgdata"
  },
  "volumes": [
    "/data:/data"
  ]
}
```

The `storage` field gives the launcher a per-container LUKS+AEAD volume mounted at `/data`; `PGDATA=/data/pgdata` keeps Postgres state inside the encrypted volume so it persists across container restarts but is unreadable outside the fleet.

### 2. private-rag

```jsonc
{
  "name":      "private-rag",
  "image":     "ghcr.io/privasys/private-rag@sha256:<pin>",
  "port":      8443,
  "hostname":  "rag.<fleet>.privasys.org",
  "internal":  false,
  "env": {
    "PRIVATE_RAG_LISTEN":        ":8443",
    "PRIVATE_RAG_CORS_ORIGINS":  "https://chat.privasys.org,https://chat.privasys.id",
    "DATABASE_URL":              "postgres://postgres:<password>@rag-db:5432/rag?sslmode=disable",
    "OIDC_ISSUER":               "https://privasys.id",
    "OIDC_AUDIENCE":             "<gateway audience for this fleet>"
  },
  "health_check": {
    "path":     "/readyz",
    "interval": "5s",
    "timeout":  "3s",
    "retries":  20
  },
  "wait_ready": true
}
```

Notes:
- `DATABASE_URL` resolves `rag-db` via the launcher's per-fleet container DNS.
- `OIDC_ISSUER` must match whatever the chat front-end signs in against. `OIDC_AUDIENCE` is the audience claim the gateway places on tokens forwarded to private-rag.
- `internal: false` so the gateway can reach `https://rag.<fleet>.privasys.org` from outside the fleet; RA-TLS terminates at the gateway and the inner connection stays inside the TDX domain.

## Order of operations

1. Generate the per-fleet Postgres password (the orchestrator's responsibility).
2. POST the `rag-db` LoadRequest. Wait for ready (the launcher will report once the health check passes; pgvector's stock image listens on 5432 immediately, so a TCP probe is enough).
3. POST the `private-rag` LoadRequest with `wait_ready: true`. The container blocks on `/readyz`, which calls the store. If Postgres is not yet accepting connections the launcher will keep retrying for the configured `retries`.
4. Add the gateway route for `rag.<fleet>.privasys.org`. The chat front-end is already pointed at the same hostname; no client-side change is needed beyond CORS.

## Operations

- Logs: `journalctl -u manager -f` on the host shows both containers' stdout.
- Migrations: `private-rag` applies its schema on every start, idempotently. There is no separate migration step.
- Backups: the encrypted `/data` LV can be snapshotted with LVM; the snapshot is still LUKS-encrypted at rest.
- Rotating Postgres credentials: change `POSTGRES_PASSWORD` and the `DATABASE_URL` in both LoadRequests, then redeploy. Existing data persists because the LUKS key is unchanged.

## Local development

A `docker-compose.yml` for laptop development is provided at the repo root:

```
docker compose up
```

This brings up the same image graph (pgvector + private-rag) but with `--insecure-no-verify` so any signed-or-unsigned JWT with a `sub` claim is accepted. Do not deploy with that flag.
